#### Numbered Flow: Admin (Login to Action)

3. **Real-Time Alert Reception:** When a victim submits an SOS, the dashboard receives the `new_alert` Socket.IO event ([AdminDashboard.js](file:///c:/Users/Zam/OneDrive/Desktop/capstone/SALBA-CDRRMO-RESCUE-APP/EmergencyApp/AdminWebApp/frontend/src/components/AdminDashboard.js#L1798-L1803)), plays the Web Audio siren (`playAlertSound`), displays a toast/banner, and plots the pin on the Leaflet map.

6. **Live Tracking & Resolution:** Admin monitors the rescuer's moving GPS pin via `rescuer_location_update` socket events ([AdminDashboard.js](file:///c:/Users/Zam/OneDrive/Desktop/capstone/SALBA-CDRRMO-RESCUE-APP/EmergencyApp/AdminWebApp/frontend/src/components/AdminDashboard.js#L1810-L1826)). Once the rescuer uploads a resolution photo or Admin clicks **Resolve** (`POST /api/reports/:id/resolve`), the team is freed back to `'available'` and the report is archived as `'resolved'` ([reportRoutes.js](file:///c:/Users/Zam/OneDrive/Desktop/capstone/SALBA-CDRRMO-RESCUE-APP/EmergencyApp/AdminWebApp/backend/routes/reportRoutes.js#L623-L735)).

## 2. REPORT SENDING/RECEIVING AND SCALABILITY

### 2.1 How Reports Are Sent and Received
- **API Endpoints:**
  - **Primary Mobile SOS Endpoint:** `POST /api/alerts` in [alertRoutes.js](file:///c:/Users/Zam/OneDrive/Desktop/capstone/SALBA-CDRRMO-RESCUE-APP/EmergencyApp/AdminWebApp/backend/routes/alertRoutes.js#L199-L849) (called by `DisasterSOS` via `sendAlert()` in [alertService.js](file:///c:/Users/Zam/OneDrive/Desktop/capstone/SALBA-CDRRMO-RESCUE-APP/DisasterSOS/DisasterSOS/services/alertService.js#L6-L48)).
  - **Web/Detailed Report Endpoint:** `POST /api/reports` in [reportRoutes.js](file:///c:/Users/Zam/OneDrive/Desktop/capstone/SALBA-CDRRMO-RESCUE-APP/EmergencyApp/AdminWebApp/backend/routes/reportRoutes.js#L156-L488).

## 5. DEFENSE PREP

### 5.1 One-Paragraph Plain-Language Pitch for Panelists
> **SALBA** is an end-to-end emergency reporting, AI triage, and rescue coordination platform built for **CDRRMO Malaybalay City**. Citizens use the **DisasterSOS** hybrid app (Android APK or iOS/Web PWA) in English or Cebuano-Bisaya to select an emergency type, capture a compressed scene photo, and transmit their GPS coordinates with a single tap. The **Node.js/Express backend** immediately records the incident in **MongoDB Atlas** and alerts the **CDRRMO Admin Web Command Center** over **Socket.IO WebSockets** in under a second, while asynchronously evaluating the report through our custom-trained **Python Machine Learning microservice (`salba-ml-service`)**. Trained from scratch on **163,052 real disaster records** and calibrated with **46-barangay Malaybalay geohazard corridors**, the AI classifies the hazard, predicts a 4-tier urgency level, filters out pranks and impossible cross-location spam bursts, and automatically escalates severity when multiple citizens report from the same 2-kilometer area. Once an administrator dispatches a rescue team, field responders use **RescuerApp** to navigate via **OSRM shortest-path routing**, stream live GPS back to both the command center and the victim's phone, automatically trigger arrival within a **50-meter geofence**, and upload a mandatory proof-of-resolution photo before closing the mission and generating official **CDRRMO SITREP Word documents**.

### 5.2 Ten Likely Panel Questions & Code-Backed Answers

1. **Q: "What happens if hundreds of citizens in the same barangay connected to the same Smart or Globe cell tower send SOS alerts at the same time? Won't your rate limiter block them?"**
   - **A:** No. In [adaptiveRateLimiter.js](file:///c:/Users/Zam/OneDrive/Desktop/capstone/SALBA-CDRRMO-RESCUE-APP/EmergencyApp/AdminWebApp/backend/middleware/adaptiveRateLimiter.js#L20-L31), we specifically engineered a **Carrier-Grade NAT (CGNAT)-aware Sliding Window Limiter**. Instead of keying by `req.ip` first, it keys by `userId -> userPhone -> x-device-id -> req.ip`, allowing 15 SOS requests per minute *per individual citizen* while still blocking single-device spam floods.
2. **Q: "What happens if a victim taps the SOS button twice or has unstable mobile data that retries the HTTP request?"**
   - **A:** We enforce 3 layers of duplicate prevention: (1) [alertService.js](file:///c:/Users/Zam/OneDrive/Desktop/capstone/SALBA-CDRRMO-RESCUE-APP/DisasterSOS/DisasterSOS/services/alertService.js#L11) attaches a unique `clientRequestId` (`sos-<timestamp>-<random>`) indexed as `unique` in [Report.js](file:///c:/Users/Zam/OneDrive/Desktop/capstone/SALBA-CDRRMO-RESCUE-APP/EmergencyApp/AdminWebApp/backend/models/Report.js#L69), so cellular retransmissions return the existing report (`isDuplicate: true` in [alertRoutes.js](file:///c:/Users/Zam/OneDrive/Desktop/capstone/SALBA-CDRRMO-RESCUE-APP/EmergencyApp/AdminWebApp/backend/routes/alertRoutes.js#L263-L274)); (2) `alertRoutes.js` (lines 277–285) rejects identical coordinates + disaster type within a 5-second window; and (3) `HomeScreen.jsx` enforces a 45-second UI cooldown after a successful send.

### 5.3 Remaining Gaps, Risks & Inconsistencies to Know for Defense
1. **No Offline SOS Store-and-Forward Queue in `DisasterSOS`:** If a citizen is in a 0-bar dead spot, `sendAlert()` fails after 15 seconds and asks the user to retry; it does not persist the unsent SOS in `AsyncStorage` to auto-send later. *Defense posture:* Explain that in emergency systems, silently queuing an SOS offline without confirmation can give a trapped victim a false sense that rescuers are already coming, so SALBA explicitly alerts the user if transmission failed while allowing them to skip heavy photo uploads on weak signals.
2. **Inference Latency Documentation vs. Actual v2 CPU Benchmark:** Comments in `app.py` (line 443) and `mlServiceClient.js` (line 17) state `< 15ms` synchronous inference. While pure vectorized tree prediction on an already-featurized vector takes `< 0.06ms` per sample, full single-request HTTP evaluation (70,016-feature regex/TF-IDF transform + 3 calibrated ensembles + spatial safeguard fusion) takes **~146ms per text report** and **~250ms per one-tap spatial report** on CPU (and **< 1ms** on cache hits). *Defense posture:* Cite both numbers (~146–250ms uncached pipeline latency, <1ms cached latency), both of which are well below the 3,000ms timeout and run asynchronously inside `setImmediate()`.
3. **Duplicate GPS Watchers in `RescuerApp`:** When a rescuer opens `MapScreen.js` (line 336), it starts a foreground `Location.watchPositionAsync` while `SocketContext.js` (line 44) already runs a global 5-second `Location.watchPositionAsync`. *Defense posture:* Both use a 5-second / 10-meter threshold to ensure UI map responsiveness even if the socket temporarily drops.
4. **Legacy v1 Files Present in Repo:** The repository still contains legacy v1 scripts (`train_models.py`, `train_models_real_data.py`, `models/*.pkl`, `DisasterSOS/backend/`, `EmergencyApp/AdminWebApp/ml_service/`) alongside the active v2 production code (`train_models_v2.py`, `models/v2/*.pkl`, `EmergencyApp/AdminWebApp/backend/`). *Defense posture:* Point panelists directly to `salba-ml-service/app.py` (lines 43–60) and `train_models_v2.py`, which prove that `models/v2/` is the active production engine.
